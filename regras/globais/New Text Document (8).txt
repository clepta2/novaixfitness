Para fechar esse ecossistema com chave de ouro — e garantindo que o seu código de validação siga a própria regra de ter menos de 200 linhas de forma modular —, entramos nas regras de Operações de Esteira e Governança Dinâmica (CI/CD).

Estas são as últimas regras que não olham apenas para o texto que você digitou na máquina, mas para o comportamento dos pacotes de dependências e metadados antes de o código ir de fato para o servidor.

37. Bloquear "Dependências Fantasmas" (Lockfile Sync)
Um erro grave que causa falhas inexplicáveis em produção ou abre portas para invasões por vulnerabilidades em pacotes de terceiros (NPM) é a falta de sincronia entre os arquivos de instalação.

A Regra: O script varre a raiz do projeto e dá BLOCK se o arquivo package.json foi modificado, mas o package-lock.json ou yarn.lock não foi atualizado no mesmo commit.

O Correto: Forçar que toda adição de biblioteca seja travada e versionada com a versão exata que funcionou na sua máquina, impedindo que o servidor de produção baixe uma versão atualizada com bugs ou alterada por hackers (ataque de cadeia de suprimentos).

38. Banir Commits Diretos na Branch Principal (Branch Protection)
Se você ou qualquer desenvolvedor puder dar um git push direto na branch main ou master sem passar pelo crivo do script de segurança, toda a automação cai por terra. Um deslize e um console.log ou uma chave secreta vai direto para o ar.

A Regra: Criar um hook de pré-recebimento ou validação local que dá BLOCK se o destino do push for a branch principal de produção de forma direta.

O Correto: O código deve obrigatoriamente ir para uma branch secundária (ex: feature/ajuste-mfa) e só entrar na principal após passar 100% liso por todas as 36 regras do seu enforce-security.js.

39. Exigir Validação Semântica de Mensagens de Commit (Conventional Commits)
Sistemas grandes precisam de históricos legíveis para rastrear bugs de segurança. Se o histórico de commits for uma bagunça cheia de mensagens como "ajuste", "agora vai" ou "corrigindo bug", descobrir quando uma vulnerabilidade foi introduzida vira um caos.

A Regra: Dar BLOCK no commit se a mensagem não seguir o padrão semântico internacional (ex: feat(auth): adiciona rate limit no mfa ou fix(db): corrige query de listagem de OS).

O Correto: Isolar as alterações por escopo de forma que ferramentas automáticas consigam ler o histórico e gerar relatórios de mudanças (Changelogs) sem intervenção humana.

40. Proibir Commits sem Verificação de Integridade Local (Pre-commit Bypass)
Desenvolvedores apressados costumam tentar burlar o linter usando a flag --no-verify no Git para pular os testes de segurança locais quando estão com pressa.

A Regra: No seu servidor de integração contínua (CI/CD na nuvem, como GitHub Actions ou GitLab CI), o script roda uma validação final redundante. Se ele detectar que a flag de bypass foi usada localmente ou se o código enviado não bater com a assinatura do validador, o deploy é rejeitado imediatamente.
