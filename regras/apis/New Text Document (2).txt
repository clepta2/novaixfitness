Estas 5 regras finais fecham o cerco técnico da sua API em 145 pontos de controle inegociáveis:

141. Controle Estrito de Depreciação de Versões (API Version Sunset)
À medida que o seu aplicativo ganha atualizações, você criará novas rotas (ex: mudando de /api/v1/treino para /api/v2/treino). Se você deixar as rotas antigas (v1) ativas para sempre sem monitoramento, elas se tornam o alvo favorito de hackers, pois costumam conter códigos legados com brechas antigas que você esqueceu de atualizar.

A Regra: Toda rota ou versão antiga da API deve ter uma data de encerramento obrigatória.

O Correto: Quando lançar a v2, injete o cabeçalho HTTP Sunset e Deprecation nas respostas da v1, avisando aos clientes que aquela rota deixará de funcionar em uma data específica. Passado o prazo, remova o código da v1 do seu Node.js para reduzir a superfície de ataque do servidor.

142. Bloqueio de Mass Assignment via DTOs Explicíticos (Data Transfer Objects)
Mesmo usando a validação com Zod no req.body, um erro comum acontece no sentido inverso: buscar um registro de usuário completo do Supabase e dar um res.json(usuario). Se o seu banco de dados tiver colunas internas como password_hash, pode_dar_desconto ou tokens internos de API, o Node vai enviar esses dados sigilosos para o front-end em React, deixando-os visíveis na aba Network do navegador.

A Regra: É proibido retornar objetos brutos vindos do banco de dados diretamente na resposta da API.

O Correto: Crie uma camada de mapeamento (DTO). O seu código filtra explicitamente apenas os campos que a tela realmente precisa exibir:

JavaScript
const userDTO = {
  id: usuario.id,
  nome: usuario.nome,
  foto: usuario.foto_url
};
res.json(userDTO);
143. Timeout Rígido no Lado do Servidor (Gateway & Request Timeouts)
Se um usuário (ou um hacker usando o Burp Suite de forma maliciosa) abrir uma requisição de upload ou uma chamada pesada e travar a conexão dele (enviando 1 byte de dados por minuto), o seu servidor Node.js pode manter essa conexão aberta indefinidamente esperando o final do pacote. Se ele fizer isso centenas de vezes, a VPS vai esgotar a tabela de conexões abertas e parar de responder.

A Regra: Toda requisição que entra na API deve ter um tempo limite de vida máximo.

O Correto: Configure um timeout global no Express ou no Nginx (ex: no máximo 15 ou 30 segundos). Se a requisição não terminar de processar ou enviar os dados dentro dessa janela de tempo, o servidor corta a conexão imediatamente (504 Gateway Timeout), liberando a memória da VPS de 4 GB.

144. Mascaramento de Mensagens de Falhas de Terceiros (Error Sanitization)
Quando a sua API faz uma chamada interna para o banco do Supabase ou para a API do Asaas e algo dá errado (como uma falha de conexão ou erro de sintaxe SQL), a biblioteca utilizada costuma retornar um erro detalhado. Se você enviar esse erro cru na resposta HTTP (res.status(500).json(error)), o atacante saberá os nomes exatos das tabelas do seu banco ou os parâmetros internos das suas credenciais.

A Regra: Mensagens de erro de infraestrutura ou de serviços de terceiros nunca devem vazar para o cliente final.

O Correto: O bloco catch captura o erro real, salva o rastro completo de forma oculta nos logs internos do servidor (onde seu bot do Telegram avisa você), e devolve para o React apenas um código e mensagem limpa: {"error": "Não foi possível processar a requisição", "code": "ERR_INTERNAL"}.

145. Assinatura de Payload entre Microsserviços / Webhooks (HMAC Verification)
Quando o Asaas avisa o seu backend que um cliente pagou uma mensalidade, ele faz isso enviando uma requisição POST para a URL do seu webhook. Se um hacker descobrir essa URL, ele pode simular requisições falsas fingindo ser o Asaas para liberar acesso premium de graça no seu app sem pagar nada.

A Regra: Webhooks e comunicações externas críticas devem exigir validação de assinatura criptográfica em nível de mensagem.

O Correto: Configure uma chave secreta de token de webhook no painel do Asaas e no seu .env. Quando a requisição chegar, o seu Node.js calcula o hash criptográfico (HMAC-SHA256) do corpo da mensagem usando a sua chave secreta e compara com o cabeçalho de assinatura enviado. Se os hashes não baterem perfeitamente, a requisição é descartada na hora.
