Se um hacker tentar quebrar a lógica sem usar o Burp Suite — atacando a memória do navegador, abusando de estados assíncronos ou explorando falhas estruturais de persistência —, o seu ecossistema vai reagir e travar o ataque se você aplicar estas 5 diretrizes de engenharia profunda:

💻 No Cliente (React / Front-end Extra)
151. Proteção contra Envenenamento de Estado de Abas Cruzadas (Tab-Nabbing & State Leak)
Se o seu usuário abrir um link externo de dentro da sua rede social (um link para um vídeo de treino no YouTube ou o perfil de um parceiro), esse link abre em uma nova aba. Se o seu código usar apenas um <a href="..." target="_blank">, a nova página aberta ganha controle parcial sobre a janela do seu app através do objeto JavaScript window.opener.

A Regra: É expressamente proibido abrir links externos sem cortar o vínculo de contexto com a página mãe.

O Correto: Todo link externo no seu React deve conter obrigatoriamente o atributo rel="noopener noreferrer". Isso impede que a página de terceiros manipule a aba do seu aplicativo ou roube dados de memória em segundo plano.

152. Bloqueio de Cache de Navegador para Páginas Autenticadas (Back-Button Cache)
Se um administrador usar o sistema e depois clicar em "Sair", o token é limpo (Regra 146). No entanto, se outra pessoa sentar no mesmo computador e clicar no botão "Voltar" do navegador, o navegador pode tentar renderizar a página anterior usando o cache de disco local, exibindo dados confidenciais na tela mesmo sem uma sessão ativa.

A Regra: Telas com dados privados devem instruir o navegador a nunca salvar cópias locais em disco.

O Correto: O seu servidor (ou a entrega dos arquivos do React) deve injetar os cabeçalhos de controle de cache: Cache-Control: no-store, no-cache, must-revalidate, proxy-revalidate. Isso força o navegador a destruir as capturas de tela locais sempre que a sessão for encerrada.

⚙️ No Backend (Node.js / VPS Extra)
153. Isolamento Atômico de Variáveis de Processo (Process-Level Sandboxing)
Se o seu servidor Node.js sofrer um erro grave em uma rota assíncrona (como uma falha de conexão não tratada ou uma divisão por zero), o processo inteiro do Node pode entrar em um estado corrompido, misturando dados na memória global ou vazando contextos de um usuário para a requisição de outro.

A Regra: É proibido armazenar estados de usuários em variáveis globais do Node.js (ex: let usuarioAtual = ... fora do escopo da rota).

O Correto: Todo dado de contexto deve viver estritamente dentro do escopo da requisição (req.user) ou ser consultado de forma atômica no Redis. O Node.js deve rodar de forma totalmente "Stateless" (sem estado), garantindo que um processo limpo atenda cada clique.

154. Limitação Estrita de Conexões por Socket no Banco (Pool Exhaustion Defense)
Se o seu Node.js abrir uma nova conexão com o Supabase/PostgreSQL para cada requisição que chega e esquecer de fechar, os recursos de rede da VPS vão se esgotar em poucos minutos. Um hacker focado em Bug Bounty pode inundar a API com requisições simultâneas lentas apenas para esgotar o pool de conexões do banco de dados e derrubar o app por completo (Connection Starvation).

A Regra: O backend deve gerenciar as conexões com o banco através de um pool fechado e controlado.

O Correto: Configure o ORM ou o driver do banco para um limite máximo estrito (ex: máximo 20 conexões ativas simultâneas no pool). Se o volume estourar, as novas requisições entram em uma fila rápida no Node em vez de tentar abrir novos sockets com o Supabase, protegendo a estabilidade da infraestrutura.

155. A Regra do "Kill-Switch" de Dependências Maliciosas (Build-Time Freeze)
Sua esteira de desenvolvimento usa ferramentas para checar vulnerabilidades (Regra 1). Mas e se uma dependência do seu projeto for atualizada automaticamente em produção trazendo um código malicioso de madrugada sem você rodar o validador manualmente?

A Regra: É obrigatório congelar as versões exatas de todas as bibliotecas no momento do build de produção.

O Correto: No seu arquivo Dockerfile e nos scripts de deploy, use estritamente o comando npm ci (Clean Install) em vez de npm install. O npm ci lê rigorosamente o arquivo package-lock.json e bloqueia a instalação se qualquer biblioteca tentar baixar uma versão milimetricamente diferente da que foi testada e aprovada por você.
