146. O Princípio da Degradação Graciosa (Graceful Degradation)
Se a VPS da Hostinger ou o banco de dados do Supabase sofrerem uma lentidão extrema por causa de um pico bizarro de acessos, o aplicativo não pode travar e mostrar uma tela branca de erro para o usuário no React.

A Regra: O sistema deve desligar recursos secundários automaticamente para priorizar as operações vitais.

O Correto: Se o Node detectar que o banco está demorando a responder, o app desativa temporariamente o feed da rede social e o chat ao vivo, mas mantém o checkout transparente e a listagem de treinos/serviços funcionando direto pelo cache do Redis. O usuário consegue comprar e usar o básico, e o sistema não cai por completo.

147. Testes de Injeção de Caos Ativos (Chaos Engineering)
Você configurou a memória Swap (na VPS), o PM2 em modo Cluster e políticas de backup automatizadas. Mas você só vai saber se isso funciona de verdade se testar no pior cenário possível.

A Regra: É obrigatório simular falhas críticas em ambiente de homologação (Staging) de forma deliberada.

O Correto: Use scripts para derrubar o container do Redis no meio de um fluxo de chat, simular a perda de conexão com o Supabase ou cortar a internet da VPS enquanto um pagamento está sendo enviado ao Asaas. Se o sistema não se recuperar sozinho (reiniciando o container via Docker ou usando a rota de contingência), a arquitetura precisa ser corrigida antes de ir para produção.

148. Rate Limiting Dinâmico Baseado na Saúde do Sistema (Adaptive Throttling)
O Rate Limit fixo (ex: 60 requisições por minuto) protege contra ataques comuns. Mas se a CPU da sua VPS de 4 GB bater 95% de uso por causa de um processo legítimo muito pesado, continuar aceitando 60 requisições de cada usuário vai derrubar a máquina por completo.

A Regra: O limite de requisições permitidas por IP no Redis deve diminuir se a saúde do servidor piorar.

O Correto: O seu backend Node.js monitora o uso de CPU e RAM da máquina. Se a VPS entrar em zona de estresse (acima de 85%), o middleware no Redis reduz automaticamente o Rate Limit de todos os usuários pela metade (ex: caindo para no máximo 20 requisições por minuto) até que o servidor esfrie e volte ao normal.

149. Bloqueio de Assinaturas de Tráfego Automatizado (Behavioral WAF)
Hackers avançados sabem como contornar o limite de requisições rotacionando milhares de IPs usando proxies residenciais ou redes Tor. Para o seu Redis, parecerá que são milhares de usuários legítimos diferentes acessando o site ao mesmo tempo.

A Regra: Monitorar o comportamento do usuário e a assinatura do navegador, não apenas o IP.

O Correto: A Cloudflare na linha de frente analisa o comportamento de navegação. Se milhares de IPs diferentes estiverem clicando exatamente nos mesmos botões, na mesma velocidade milimétrica, e com a mesma assinatura de cabeçalhos internos (JA3 Fingerprint), a Cloudflare identifica que é uma botnet coordenada e bloqueia todos os IPs antes mesmo que eles toquem na sua VPS da Hostinger.

150. A Regra do Log de Auditoria Imutável (Write-Once-Read-Many)
A tabela de logs de auditoria de modificações que estruturamos é excelente. Mas se um hacker conseguir invadir o seu banco de dados com privilégios de superusuário, a primeira coisa que ele fará será rodar um comando DELETE FROM auditoria_modificacoes para apagar os rastros dele e você nunca descobrir como ele entrou.

A Regra: Os logs de segurança nunca devem poder ser alterados ou apagados, nem pelo administrador do sistema.

O Correto: Configure as regras de segurança (Políticas RLS) no Supabase de modo que a tabela de auditoria só aceite comandos de inserção (INSERT). Comandos de UPDATE ou DELETE nessa tabela são bloqueados diretamente na raiz do banco de dados. O rastro do sistema vira uma linha do tempo imutável e à prova de adulteração.
