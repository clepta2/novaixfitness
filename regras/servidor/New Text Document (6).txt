Se formos além dos ataques de software e de rede, entramos na última fronteira da segurança digital: os Ataques de Infraestrutura Física, Lógica de Negócio Inversa e Vazamento Indireto (Regras 126 a 130).

Para fechar o tabuleiro de forma absoluta e garantir que o seu aplicativo (seja o Novais Fitness, a Diff Store ou qualquer outro) seja uma fortaleza inexpugnável, precisamos neutralizar os últimos 5 meios que os atacantes usam para burlar sistemas sem nem tocar na API principal:

126. Ataques de Deserialização Insegura (RCE via Payload)
Muitos sistemas usam bibliotecas para compactar, ler ou converter objetos complexos enviados pelo cliente (como ler um arquivo de configuração, um backup de treino ou dados de importação).

O Ataque: O hacker não muda apenas os dados no Burp Suite; ele envia um objeto modificado contendo trechos de código executável ocultos dentro da estrutura de dados. Se o seu Node.js ler esse objeto usando funções inseguras (como um eval() mascarado ou parsers antigos), o servidor executa o código do hacker direto no Linux, dando a ele o controle da VPS.

A Defesa: Nunca usar funções de avaliação dinâmica de strings. Para ler e validar dados complexos e JSONs estruturados, use estritamente o Zod (Regra 12) ou esquemas de validação rígidos que descartam qualquer propriedade estranha ao payload esperado.

127. Sequestro de Subdomínios Ociosos (Subdomain Takeover)
À medida que o seu sistema cresce, você começa a criar subdomínios no DNS da Hostinger ou Cloudflare para ferramentas externas (ex: blog.novaisfitness.com apontando para o Medium ou suporte.diffstore.com apontando para o Zendesk).

O Ataque: Se um dia você cancelar o serviço externo mas esquecer de apagar a linha de apontamento (CNAME) no seu painel DNS, o hacker pode ir na plataforma externa, assinar o plano e reivindicar aquele subdomínio para ele. O hacker passa a ter uma página falsa rodando exatamente sob o seu domínio legítimo, facilitando o roubo de cookies e phishing.

A Defesa: Auditoria periódica na tabela de DNS da Cloudflare/Hostinger. Se um serviço não é mais utilizado, a entrada de DNS deve ser deletada imediatamente.

128. Ataques de Forçamento de Erro para Information Disclosure
Hackers provocam erros propositais no sistema enviando payloads com caracteres corrompidos, tipos de dados errados (enviando uma string onde o código espera um array) ou estourando os limites de tamanho de arquivos.

O Ataque: Se o seu Node.js ou Supabase não tiver um tratador de erros genérico, o sistema pode exibir na tela do React uma mensagem interna de erro expondo a estrutura das pastas do Linux, nomes de tabelas do banco de dados ou versões de módulos do Node. O hacker usa essas informações para mapear vulnerabilidades exatas da versão do seu sistema.

A Defesa: O middleware de erro global do Node deve capturar a falha técnica, salvá-la de forma oculta nos logs internos sanitizados (Regra 115) e devolver para o cliente apenas uma mensagem padrão: {"error": "Internal Server Error", "code": 500}.

129. Abuso de IDOR em Upload de Arquivos (Insecure Direct Object Reference)
Quando o cliente envia uma foto de perfil, um comprovante de pagamento ou uma imagem de Ordem de Serviço, o arquivo vai para o Storage do Supabase e gera um link público.

A Ataque: Se o nome do arquivo gerado for sequencial ou previsível (ex: comprovante_124.jpg), o hacker altera o número para comprovante_123.jpg direto na URL do navegador para ver e baixar documentos, fotos e dados privados de outros clientes do sistema.

A Defesa: Todo arquivo que entra no seu sistema deve ter o seu nome original descartado pelo Node.js e substituído por um UUID v4 longo e aleatório combinado com um hash criptográfico (ex: f81d4fae-7dec-11d0-a765-00a0c91e6bf6.jpg). Além disso, use as Políticas de Linha do Supabase (RLS) para garantir que apenas o dono do arquivo tenha a chave de leitura do link.

130. Ataque de Inundação de Memória via JSON Inundado (JSON Bomb)
O hacker envia uma requisição HTTP legítima para a sua API, mas o corpo do JSON é gigantesco, contendo um objeto aninhado centenas de vezes dentro de si mesmo ou um texto repetido gigas de vezes.

A Ataque: Quando o seu servidor Node.js tenta processar e ler esse JSON usando o padrão express.json(), a CPU da VPS trava tentando varrer e interpretar aquela estrutura massiva na memória, derrubando a aplicação por falta de recursos (DoS por esgotamento de CPU).

A Defesa: Limitar de forma rígida o tamanho máximo do payload que o seu servidor aceita processar. No Express, configure o limite máximo de corpo para algo seguro (ex: no máximo 10kb ou 1mb para uploads):

JavaScript
app.use(express.json({ limit: '10kb' }));
Se o hacker tentar enviar uma bomba de dados, a própria VPS rejeita a requisição imediatamente antes de gastar memória tentando ler o arquivo.
