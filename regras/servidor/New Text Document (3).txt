Essas últimas cinco regras se aplicam perfeitamente à sua stack (Node + React + Redis + Docker + VPS Hostinger + Supabase) e servem para garantir que o seu aplicativo continue de pé mesmo que o servidor sofra um pico de acessos massivo e simultâneo (como a Black Friday ou o lançamento de um recurso viral).

Aqui estão as regras finais para travar o tabuleiro em 125 pontos de controle:

121. O Padrão de Trava Distribuída (Redis Redlock)
Você já configurou transações atômicas no Supabase para evitar duplicação de pontos e cupons. Mas imagine que o seu Node.js está rodando em modo Cluster (vários processos ao mesmo tempo na VPS). Se duas requisições idênticas baterem em processos diferentes do Node no exato mesmo milissegundo tentando alterar o mesmo recurso pesado, a verificação local do código pode falhar antes de tocar no banco de dados.

A Regra: Operações que alteram saldos financeiros ou inventário crítico devem usar Trava Distribuída (Distributed Lock) no Redis.

O Correto: O processo do Node que recebeu a primeira requisição cria uma chave temporária no Redis com um tempo de vida de segundos (SET recurso:bloqueado TRUE NX EX 5). Se o segundo processo tentar mexer no mesmo recurso, o Redis recusa. O dado fica blindado em nível de infraestrutura, impedindo qualquer brecha de concorrência simultânea.

122. Banir Consultas N+1 no ORM (Gargalo de Memória de Banco)
Ao listar dados na tela do React (como os posts do feed junto com os dados e foto de perfil de cada autor), um erro clássico de código é fazer o Node buscar a lista de 20 posts e, depois, fazer um loop rodando 20 consultas individuais no Supabase para pegar o perfil de cada autor. Isso se chama problema N+1 e destrói o processamento do banco.

A Regra: É proibido rodar loops de requisições ou consultas de banco para buscar dados correlacionados.

O Correto: O seu backend Node.js deve usar JOINs explícitos no SQL ou configurar o ORM (Prisma/Drizzle) com include/relations para trazer o post e o autor em uma única viagem estruturada ao banco de dados, reduzindo o uso de rede e CPU da VPS a quase zero.

123. A Regra do Cache de "Invalidação por Evento" (Write-Through Cache)
Nós já configuramos a estratégia de cache no Redis para dados que mudam pouco. Mas e se o usuário alterar a foto de perfil ou o nome dele? Se o cache no Redis durar 1 hora, o React do usuário vai continuar mostrando o nome antigo por 1 hora, gerando a sensação de que o app está com bug.

A Regra: Toda rota de mutação de dados (PUT/PATCH/DELETE) que afete um dado cacheado deve, obrigatoriamente, limpar o cache.

O Correto: Sempre que o usuário atualizar os dados no Supabase, o Node executa imediatamente um comando DEL cache:usuario:id no Redis. Na próxima vez que o perfil for requisitado, o Node não achará o cache, buscará o dado atualizado no banco e salvará a nova cópia. O dado fica sempre sincronizado em tempo real.

124. Compactação de Payload HTTP na VPS (Gargalo de Largura de Banda)
À medida que a sua rede social ou sistema cresce, os JSONs enviados pelo Node.js para o React (com dezenas de mensagens do chat ou posts do feed) começam a consumir muita largura de banda da rede da Hostinger. Se a sua VPS saturar a taxa de transferência de dados da placa de rede, o app vai parecer lento, mesmo com a CPU em 5%.

A Regra: Ativar obrigatoriamente a compactação de dados no servidor de produção.

O Correto: Ative o middleware compression no Express (Node.js) ou configure o container do Nginx que serve o React para usar Gzip ou Brotli. O servidor compacta o JSON pesado antes de enviar e o navegador do cliente descompacta instantaneamente. Isso reduz o tamanho das transferências de rede em até 70%, acelerando o carregamento do app no celular do cliente.

125. Isolamento de Contexto de Desenvolvimento (O Teste dos Três Ambientes)
A regra operacional final: É expressamente proibido que a sua máquina local de desenvolvimento ou o seu script de teste tenha as chaves de produção do Asaas ou as URLs reais do banco de dados do Supabase. Um único comando errado de migração de banco executado na sua máquina poderia apagar o sistema real em produção.

O Correto: Isolar o ecossistema em três instâncias rígidas de .env:

Development (Local): Node local, Docker local do Redis e Supabase Local/Sandbox.

Staging (Homologação): Uma réplica idêntica na nuvem para você testar no Burp Suite antes do lançamento.

Production (Produção): A VPS da Hostinger rodando o código real, trancada e acessada apenas via chaves criptográficas SSH.
